# First End-to-End Run: ERC4626 Inflation Fixture

Date: 2026-06-08

Fixture: `examples/erc4626_inflation_fixture/`

Goal: validate whether ZeroPath can ingest a small vulnerable vault, infer the
right protocol shape, generate a useful hypothesis, attempt proof generation,
and refuse final report export when evidence is insufficient.

## Ground Truth Fixture Test

Command:

```bash
forge test
```

Important output:

```text
Ran 1 test for test/VulnerableVault.t.sol:VulnerableVaultTest
[PASS] testDonationInflationProfitable() (gas: 2865227)
1 tests passed, 0 failed, 0 skipped
```

The fixture itself demonstrates the donation-sensitive inflation pattern. The
test is hand-written and is not generated by ZeroPath.

## ZeroPath Commands Run

From `examples/erc4626_inflation_fixture/`:

```bash
zeropath init
zeropath ingest --repo .
zeropath understand
zeropath hunt --mode critical --limit 5
zeropath candidates list
zeropath candidates show ZP-001
zeropath prove ZP-001 --backend foundry
zeropath judge ZP-001
zeropath report ZP-001 --format code4rena
zeropath memory rejected
```

Local execution used the repo virtualenv binary:
`../../.venv/bin/zeropath`.

## Validation Answers

- Did ZeroPath detect the protocol as vault-like? Yes. `ingest` reported
  `protocol_type vault`, and `understand` reported `type vault`.
- Did the share-inflation invariant appear? Yes. The candidate references
  `INV-VLT-001`, and the intent snapshot included two vault invariants.
- Did an attacker/victim transaction sequence appear? Yes. The candidate
  includes attacker donation, victim deposit, and attacker redemption steps.
- Did it identify required state? Yes. The candidate lists low/zero share
  supply, attacker ratio manipulation, and victim under-minting.
- Was the PoC skeleton useful? Partially. It carried candidate context and the
  proof plan artifact, but it did not materialize contracts, calls, or profit
  assertions. It is not yet a proof.
- Did judge block report export without sufficient proof? Yes.
- Did any command silently overclaim? The previous Forge behavior was fixed:
  a no-test run is now `no_tests`, not `passed`.
- Did memory store rejected candidates and useful lessons? Not in this run.
  The candidate was `needs_evidence`, so storing it as rejected would be a bad
  lesson. Fatal rejected hypotheses should be stored with explicit reasons.

## Weaknesses Found

- The protocol summary still lists helper/test contracts (`MockERC20`, `Actor`,
  `VulnerableVaultTest`) even though the candidate root cause is now correctly
  localized to `VulnerableVault`.
- The generated Foundry PoC is a skeleton, not an executable exploit test.
- `prove` does not synthesize concrete deployment, minting, attacker donation,
  victim deposit, redemption, or profit assertion calls.
- Judge correctly blocks the report, but the next milestone needs a path from
  candidate/state plan to an executable proof.
- Memory avoids storing this `needs_evidence` candidate, but there is no
  higher-level learning loop to avoid repeated insufficient-evidence candidates.

## Next Milestone

Make ERC4626 inflation fully executable:

1. Read candidate root-cause and entrypoint metadata.
2. Select or generate the required mock token and vault setup.
3. Generate a Foundry test with concrete attacker/victim calls.
4. Assert profit or victim share loss.
5. Mark proof as passed only when that test executes.
6. Let judge mark the candidate report-ready only after source, state, duplicate,
   known-issue, proof, live/local config, and measured-impact evidence are set.
